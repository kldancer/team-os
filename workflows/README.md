# 通用工作流合同

## 结果生命周期

```text
intake → ready → doing → verifying → done
                   └────→ waiting ──→ doing
```

| 状态 | 进入条件 | 离开条件 |
| --- | --- | --- |
| `intake` | 收到目标但边界尚未闭合 | 目标、非目标、项目与授权明确 |
| `ready` | 输入、负责人、读写集合、验收和预算齐全 | 负责人开始执行 |
| `doing` | 正在分析或实施 | 进入验证，或写明外部等待 |
| `verifying` | 实现已稳定，按适用 Gate 取证 | 验收闭合或返回修复 |
| `waiting` | 需要新的用户决定、外部事实或授权 | 恢复条件满足 |
| `done` | 实现、适用验证、真实事实和披露闭合 | 终态 |

## 标准反馈环

1. 选择项目并读取适配器；
2. 用项目权威和 Team OS 通用制度建立结果卡；
3. 识别最短可证伪路径和必要角色；
4. 在互斥写集合下执行，保持一个结果负责人；
5. 按项目机器计划或明确验收验证；
6. 形成实现、证据、剩余风险和决策的紧凑交接；
7. 稳定经验回到正确权威，动态流水留在 `.work`。

## 交接包

交接只传递：目标与当前状态、已作决策及理由、变更路径、验证命令与结果、证据引用、未决风险、下一步和停止条件。不得用完整聊天记录代替交接，也不得在交接中包含密钥或 Provider 认证内容。

具体项目的命令、Gate、并发上限、生产分波与提交方式不在这里定义，必须从项目适配器指向的项目权威读取。

默认的人机入口和 Plan Manifest 协议见 [对话式规划与确定性组织](conversational-orchestration.md)。
