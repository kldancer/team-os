# 对话式规划与运行时组织

## 1. 用户入口

日常工作使用当前选定的 Agent harness。用户先在同一个 Session 中讨论想法、方案和取舍；普通讨论不要求填写任务表，也不自动创建协作单元。用户明确说“按结论开始推进”后，当前会话把已经讨论清楚的结论编译成一个结果合同并直接推进。

用户不必重复填写 `outcome`、`nonGoals`、`authority`、`scope`、`acceptance` 和 `stopConditions`。自然语言需求由当前 Owner 按 [`request-compiler.md`](request-compiler.md) 和项目事实自动补齐；只有产品决策、生产/远端写、删除、凭据或事实冲突才需要回问。未命中高风险例外时，默认采用 `@plan_owner`、`solo` 和最短可验证路径，并在执行前披露自动补全的关键假设。

讨论结论随后要实施时，只有跨边界、未决依赖或高风险写入才形成覆盖型实施规划；单路径修复或刷新用最小结果合同直接执行，不增加规划仪式。长期产品合同直接进入项目正式设计；实施规划保留本次必要的决策基线、失败面、DAG、保护和运行验收映射。

该表达只改变“讨论 → 实施”的阶段，不扩大权限。它可以覆盖当前项目内的本地实现、文档和适用验证；Git、远端、生产、破坏性操作和数据删除仍按用户授权与项目合同处理。

## 2. 当前 Session 是结果负责人

当前 harness Session 负责：

1. 识别平台总控仓库和最小目标 workspace；
2. 读取项目 `AGENTS.md`、实施规范、相关正式设计和机器计划；
3. 从已有讨论收敛结果、非目标、读写集合、验收、预算和停止条件；只读取会改变路径的项目事实；
4. 默认由当前 owner 模型在本 Session 端到端完成，只在互补证据、互斥写集合或高风险独立验证足以覆盖协调成本时创建可检查的独立执行单元；
5. 为协作任务声明目标、非目标、输入、写集合、禁止修改、验证、预算以及完成/停止条件；
6. 维护依赖 DAG、单一写入责任、跨 Lane Gate 和最终综合。

复杂模块、跨服务结果或两个以上独立证据域必须在实施前显式报告 `solo` 或推荐的独立执行单元数量。Codex 中使用侧栏可见、拥有独立 Session 的任务；OMP 中使用 Agent Hub 可见、可 steer/stop、写集合隔离的 worker；Pi 只有在扩展通过 Harness Gate 后使用 subagent。当前 Session 负责综合，各执行单元按授权和证据需求选择适用模型/档位。

这不是常驻的“总管 Agent”，也不要求用户预先分配前端、后端或测试。角色是当前任务中的职责，专业能力按事实缺口加载。

## 3. 最小结果合同

```text
outcome: 用户最终能验证什么
nonGoals: 本次明确不做什么
authority: 需要读取的项目权威
ownerRole + capabilityProfileIds
scope: read / write / excluded
acceptance + validation
budget: target / hardStop
stopConditions
topology: solo 或最小协作拓扑
```

结果合同通常保留在当前 Session 上下文；需要跨 Session、跨 harness 或长时间恢复时，把最小可验证字段写入项目既有机器状态或 `.work`。不为普通任务复制完整 Transcript，不在 Team OS 建中央任务数据库。结果负责人应先读取会改变路径的真实项目上下文，不要求用户重复填写已知事实，也不为常规任务预先生成完整影响地图。

用户明确要求长期 Goal 时，一个 outcome 只建立一个 durable outcome。Codex 可投影到原生 goal，OMP 可投影到 Session todo/checkpoint，Pi 可由已准入扩展投影；项目机器状态或 `.work` 中的 outcome 才是跨运行时恢复依据。运行时 Goal 不替代覆盖型实施规划、项目机器任务或验收证据，重规划和批量修复不得重复建立。

## 4. 协作任务与 Session

| 场景 | 策略 |
| --- | --- |
| 同一结果中的连续工作 | 复用当前 Session，保持上下文连续 |
| 独立只读证据 | 创建有界、可检查的独立执行单元，首轮不共享候选结论 |
| 写集合互斥且分别可验收 | 创建隔离执行单元并声明各自写集合，一次集成 |
| 高风险实现 | 单写负责人完成候选，独立验证者只写证据 |
| 无关的新结果 | 新建独立 Session/任务；角色名称不要求新增长期人物 |

`cwd` 是启动位置和项目指令发现锚点，不是访问权限本身。实际可读写范围由 harness/操作系统权限、用户授权、项目合同和任务写集合共同约束。

## 5. 意图路由

| 输入 | 处理方式 |
| --- | --- |
| “排查/分析为什么” | 只读可证伪诊断 |
| “定位并整改/修复” | 同一诊断任务完成复现、根因保护、最小修复和目标验证 |
| “设计/规划新模块” | 只形成产品合同和覆盖型实施规划，不默认写实现 |
| “按以上结论开始推进” | 当前结果负责人读取项目权威后直接端到端交付 |

诊断任务不需要结论文档或 program 规划；大模块也不能以一串 quick-fix 绕过场景和 failure-surface 覆盖。首次运行态验证后发现的同一 outcome 遗漏回到原任务和原规划 revision，本地成批闭合后再生成一个冻结候选。

## 6. 状态、证据与恢复

用户只需理解：讨论中、执行中、验证中、等待你、完成。Harness Session 保存短期连续性；项目 `.work` 保存可恢复状态和动态收据；正式设计保存长期合同；Team OS 只保存跨项目稳定方法。恢复时先读当前 Session 和项目机器状态，不从终端输出、文件时间或人物记忆猜测进度。
