# 上下文经济与按需派工

## 1. 默认原则

上下文最贵的部分是重复读取、角色交接和等待。每个结果默认由一个 `@owner` 完成，先读取会改变路径的最小事实。不要为了满足角色数量、规划比例或派工比例启动额外 Session。

同一事实只需要一个读取者；如果 Worker 返回证据包，必须带路径/行号、事实与推断的区分、证明了什么和仍缺什么。

### 机器权威索引

项目若提供设计/合同 catalog、代码索引或影响分析入口，需求、症状或代码路径归属不明时先查询，再读取唯一 owner 与项目声明的有界 context pack。修改稳定合同时先做 impact，沿项目返回的实现根和验证入口下钻；索引不存在或目标已明确时直接读取目标片段。Team OS 只登记入口，不复制项目节点、合同、数量预算或生成图。

## 2. 三类角色

- `@owner`：结果、决策、实现、验证和最终综合的唯一负责人。
- `@worker`：只在独有证据、互斥写集合或批量机械工作成立时启用；必须使用自足派工包。
- `@reviewer`：只在高风险或明确要求时启用；只读，不修改实现。

UI、视觉、数据库和 SRE 是能力标签。它们不会自动生成角色链。

## 3. 派工判断

适合 solo：局部修复、单服务功能、单组件构建和目标 smoke。

适合派 worker：两个独立事实源、批量重复操作、互斥文件集合或长时间叶子命令。

适合派 reviewer：权限、数据、跨服务合同、生产风险或用户明确要求独立挑战。

所有派工包声明绝对路径、读写集合、禁止修改、步骤、验收、时间预算和停止条件。worker 不从设计正文推断授权，不启动其它 worker，不提交、不推送、不做生产写。

## 4. 模型绑定

角色与模型分离。模型可以在当前会话或 Profile 绑定到 `owner`、`worker`、`reviewer`；绑定变化要披露 resolved model、作用域和恢复方式。路由检查用于诊断配置漂移和成本，不参与任务 close。

## 5. 长命令和恢复

长命令必须输出：实际命令、阶段、日志路径、预计耗时、hard timeout 和止损动作。构建、部署、完整 e2e 和长回归放进项目 Task Runner；前台只等待能够判定用户结果的最小验证。

任务状态放在项目 `.work/tasks/<task-id>/`，包括事件、命令日志、计划、收据和恢复状态。工作台关闭后可以通过项目命令 `status`、`tail`、`resume` 继续。

## 6. 失败预算

同一验收点连续失败达到项目定义的预算，或根因越出派工包写集合，立即停止当前方法并回到 owner 重新定界。禁止通过更换角色、重复构建或扩大测试掩盖没有新事实的等待。
