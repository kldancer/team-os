# UI 设计与前端交付工作流

本文是跨项目 UI 领域方法，不是第二套交付流程。项目自己的设计系统、业务合同、机器 Gate 和安全规则优先；一个结果仍由原流程所有者负责。适用于设计、实现与验收，不意味着收到分析请求就可以改代码或部署。

## 1. 三种工作模式

| 模式 | 输入与起点 | 最短闭环 |
| --- | --- | --- |
| 既有页面迭代/缺陷修复 | 当前页面、用户症状、现有 token 与组件 | 复现或取得基线 → 最小修改 → 目标渲染和行为核验；不新增 moodboard 或完整规划 |
| 新页面/新视觉方向 | 用户任务、内容、品牌和实现约束 | 明确方向 → 可审阅代表屏与关键状态 → 固定设计基线 → 完整纵向切片 → 视觉与行为反馈 |
| 按稿忠实还原 | 指定设计图/Figma/原型、素材和适配要求 | 提取可实现约束 → 复用组件实现 → 同条件对照；不擅自重新设计 |

功能新增但视觉体系不变时优先沿用既有模式。不要按任务大小强制生成多套方向、固定页数、图片数量或五个串行 Gate。修复走诊断所有者，仅设计走设计所有者，已定方案实施走交付所有者。

先区分服务对象；“前台/后台”是体验用途，“前端/后端”是技术边界，不能混为角色或权限等级：

| 体验用途 | 首要设计依据 | 避免的误用 |
| --- | --- | --- |
| 官网、品牌和内容展示 | 读者理解顺序、可信内容、核心行动、品牌与素材；公开发现有需求时考虑搜索与分享元数据 | 机械套管理台的高密度表格，或凭空添加营销承诺 |
| 用户前台、自助服务 | 发现 → 判断 → 操作 → 结果；解释成本、进度和恢复路径，按实际设备设计 | 把前台等同于营销页，隐藏用户完成任务必需的信息 |
| 管理后台、运营工作台 | 高频扫描、比较、筛选、批量处理与追踪；危险动作的影响范围清楚 | 按数据库表生成菜单，用大 Hero、同质 KPI 卡和装饰图表占据工作区 |

同一项目可复用语义 token 和基础组件，但不同受众允许有依据的密度与布局变体；不为了统一而让所有页面长成同一个模板。

## 2. 最小设计基线：先把“好”说明白

在既有设计或本任务合同中补齐会改变实现的缺口，不要求用户填写表格，也不把每项拆成独立文档：

| 约束 | 需要回答的问题 |
| --- | --- |
| 用户与任务 | 谁在什么入口完成什么主动作？成功与失败如何看得见？管理台的扫描/比较与官网的品牌表达不能套同一布局 |
| 信息与状态 | 真实字段、内容层级、主次操作、加载/空/错误/权限/提交中和恢复路径是什么？沿用现有业务状态，不发明后端能力 |
| 视觉目标 | 参考是“灵感”还是“批准还原目标”？参考版本、视口、主题、字体、布局密度和允许偏差是什么？ |
| 实现映射 | 复用哪些 token、组件变体、图标和素材？缺失素材如何取得或替代？哪些是 DOM，哪些才是位图资产？ |
| 适配与质量 | 支持哪些屏宽、长文本/中文、缩放与输入方式？哪些视觉、行为、可访问性与性能要求必须验收？ |

已有参考不等于用户批准了所有细节。仅重大品牌方向、信息架构或业务选择不明确时请求决策；已授予设计裁量的常规细节由负责人选定并说明，不逐步等确认。

新视觉方向先做能揭示主要风险的代表屏及关键状态；继承样板即可表达的页面无需逐页先画高保真稿。可用仓内交互原型、Figma 或概念图，以可审阅且能落地为准；不强制购买工具或先生成整页位图。已有框架、token 和组件足够时不迁移技术栈。

### 2.1 从模糊审美到可实施约束

负责人从讨论和现有仓库补齐以下内容，写入原设计/任务合同；不是要求用户先提供完整设计简报：

- **任务和阅读顺序**：角色 → 高频任务/高风险误操作 → 业务对象 → 页面与导航 → 主次信息。主动作、比较对象与渐进披露由任务决定，不按字段表排序。
- **视觉主张**：一句描述领域与气质的话，加可观察的层级、密度、排版、表面和强调方式。例如运营台的“安静、精确”需要落实为异常优先、金额对齐、克制状态色，而不是只写“高级”。
- **参考提炼**：标明每个参考借鉴什么、不借鉴什么；把网格、字阶、留白节奏、形状和状态映射到现有 token/组件。没有参考时可用现有优质页面或先产出可审阅方向，不凭空声称已批准。
- **内容和素材**：用合成/脱敏的领域样本覆盖中文长标题、缺失值、极端数值与真实状态。明确单位、日期/时区、货币精度和业务术语；不用真实秘密或占位套话掩盖布局风险。
- **代表屏选择**：挑能覆盖布局家族和最高风险交互的最小集合；后台常见列表、详情/表单、分析页只是候选。优先复用已认可样板，不固定三页，也不为凑样板新增产品页面。

代表屏稳定后，把复用规则和允许变体留在项目权威中再扩展页面。字体、行高、圆角、断点和动画时长使用项目基线，不把研究示例数值当通用标准。视觉灵感不能替代交互与可访问性依据。

## 3. 设计到代码：防止“图很好、落地失真”

- 先核对字体来源、图标集合、素材使用权、裁切/比例、主题变体和缺失资产；不能把截图中的字、按钮、表格烘焙成背景图来伪装完成。
- token 的值与组件接口由项目代码或其明确指定的设计系统维护；规范链接来源，不维护第二份数值表。Figma 与代码不一致时先确定目标基线，不任选一方覆盖另一方。
- 对新视觉先验证“页面壳 + 一个有真实交互的核心区域”，尽早暴露布局和组件不可行性；之后按业务切片扩展，不机械逐 section 停工。
- 分离布局、领域状态、API 和测试夹具；复用现有 primitive，按真实变化原因划分组件，不以文件行数或目录模板强制拆分。
- 参考缺少窄屏或失败态时，依据业务合同补充明确适配，不靠整页缩放或隐藏主操作蒙混过关。桌面专用产品按声明的最窄支持宽度验收，不自动承诺手机功能。
- 视觉改造不擅改路由、权限、数据来源、表格列含义和写操作。发现业务缺口反馈给同一 owner，纳入同一结果的覆盖合同，不以 CSS 掩盖。

### 3.1 纵向切片与前后端合同

一次切片围绕一个用户结果：入口 → 输入/查询 → 业务判断与授权 → 写入或异步操作 → 可见结果 → 刷新/重新进入后的事实。不是先铺完所有静态页面再接 API。只设计或原型任务可用明确标注的模拟数据，不冒充真实集成。

涉及数据或交互时，引用现有机器 schema/接口和状态权威，只补实际变化的边界：

| 边界 | 要明确的内容 | 适用验证 |
| --- | --- | --- |
| 查询与显示 | 请求/响应类型、空值、单位、分页/排序/过滤的作用范围；哪些状态可进入 URL | 真实字段映射、长数据、筛选后翻页与浏览器返回；错误响应不转成成功空态 |
| 身份与权限 | 可信身份来源、角色/租户/资源范围、字段和动作的授权规则 | UI 可见性与后端拒绝分别核验；跨角色/租户请求不能因猜到 ID 而成功 |
| 提交与异步 | 校验、重复提交/幂等、并发冲突、超时、取消语义、部分成功、成功证明 | pending 不等于成功；响应丢失后按合同查询结果，不盲目重复有副作用的写入 |
| 状态所有权 | 远端实体与请求缓存、URL 导航状态、本地选中/弹层、未保存草稿各由谁维护 | 不将远端实体复制到多个全局 store；请求乱序不覆盖新选择；缓存键隔离身份与过滤条件 |
| 写后恢复 | 更新/失效哪些列表和详情、保留哪些输入、重试/刷新/重进如何一致 | 不只看 Toast；读取权威结果验证完成，跨账号切换不显示上个账号缓存 |

服务端仍对输入及每次受保护请求授权，隐藏/禁用按钮只改善体验；不把“有 RBAC 页面”当作安全证明。[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

采用现有请求层与状态管理方式，不因上述分层而新增库或状态机框架。乐观更新只用于合同允许、可恢复的操作；收费、权限和不可逆操作不能用成功动画代替服务端确认。异步场景继承项目完整失败面要求，不另建平行轮询器。

### 3.2 常见页面的任务与状态模式

只加载当前页面涉及的行；这是防遗漏提示，不是自动扩充需求的组件功能清单。排序、导出、批量、SSO 等没有业务需求或后端能力时不擅自添加。

| 场景 | 设计/实现要点 | 容易遗漏的失败面 |
| --- | --- | --- |
| 登录与会话恢复 | 沿用已有认证能力；清楚的标签、字段错误与合法返回路径 | 过期、鉴权拒绝、重复提交；不将口令写入 URL/持久草稿，敏感输入保留遵守安全合同 |
| 用户发现与详情 | 搜索/分类 → 关键信息比较 → 详情 → 主动作 → 可见结果；按任务渐进披露 | 无匹配、内容下架、不可用操作与返回后位置丢失；不伪造推荐或状态 |
| 表单与编辑 | 按业务语义分组、可见 label、字段/全局错误定位、提交反馈；草稿与离开保护按数据风险设计 | 校验失败保留安全输入、并发修改、未保存关闭、权限失效；不能无条件自动重试 |
| 列表与筛选 | 列按扫描/比较顺序，数值单位与对齐稳定；筛选条件可见且可清除 | 首次为空与筛选为空不同；筛选/排序影响分页和选中集合，返回/刷新状态有合同 |
| 批量操作 | 明确“本页/已选/全部匹配”的集合语义、数量和影响；危险动作按风险确认 | 部分失败逐项可定位，重试只针对适用失败项；筛选变化不悄悄扩大目标集合 |
| 详情与权限配置 | 对象、状态、关联历史和允许动作层级清楚，权限使用现有 capability 语义 | 对象已删除、只读/可编辑差异、跨租户资源和字段级拒绝 |
| 报表与分析 | 总体判断 → 驱动原因 → 明细/行动；导出/打印只在范围内提供 | 日期口径与页面过滤一致，导出仍授权；无数据不是数值为零 |

加载、刷新中/旧数据、成功、首次空、筛选空、字段错误、网络错误、未登录、无权限、冲突、部分失败是候选状态；仅实例化业务可达状态及相邻转移。控件另核对 hover、focus、disabled、selected，不将控件反馈误造为后端业务状态。数据展示应按重要性、操作频率与关联组织，并处理超长和空内容。[Ant Design 数据展示](https://ant.design/docs/spec/data-display/)

### 3.3 动效和图表：先说明意义，再选工具

**动效**只在有助解释因果、层级、空间连续性或反馈时采用。定义触发条件、结束状态、重复点击/中断/卸载处理；不阻塞输入、不无限装饰循环。减弱动画时保留同等信息，焦点和状态播报不能依赖动画结束。简单变化先用现有组件或 CSS，需要复杂编排才评估新依赖。

**图表**先写用户问题 → 数据口径/单位/时间窗 → 比较基线 → 编码方式 → 交互/后续行动。趋势可用折线，类别比较可用条形，分布可用直方/箱线；能用一句话或表格回答时不强行画图。不用装饰性 3D、无意义仪表盘或颜色堆叠代替数据解释，也不一概禁止业务确有需要的图形。

图表处理空值与零值、缺失区间、异常值、时区/聚合口径及可比坐标轴；精确读数提供可达明细或文本，不能只有鼠标 tooltip 和颜色。适配容器变化，按真实数据规模评估渲染，复用现有图表库，不默认安装 ECharts/D3。交互组件的键盘与语义模式可查 [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/)，使用 ARIA 属性本身不等于可访问性完成。

## 4. 两条反馈环，共用一个负责人

视觉环：目标基线 → 浏览器实际渲染 → 比较可见差异 → 修正 → 再看。

功能环：用户路径与失败面 → 行为/API 验证 → 修正 → 重跑受影响验证。

两者可以共用一次浏览器会话、夹具和证据，但不能互相替代。加载、资源可用和布局稳定的条件要明确；不要固定 sleep 或仅凭 DOM 存在就认定页面正确。优先 DOM、可访问性树、网络和既有 fixture；只有这些无法观察目标状态时才增加受控的开发态只读观察接口，不默认公开应用全局状态。

### 4.1 视觉证据与差异处理

布局、字体、主题、图像、动效或溢出变化需要目标区域的渲染检查，即使没有 API/鉴权变化。纯测试或不可见重构可用有效基线与行为保护说明不适用。局部改动只核验目标及直接受影响区域；共享 token、容器或 primitive 变化才扩大到代表性消费者。

对照固定视口、缩放/DPR、角色、主题、数据状态和字体就绪条件。用目标图与当前图核对结构/内容、字体换行、间距密度、裁切和交互状态。差异只记实际存在且影响验收的项，不凑固定数量或主观百分比分数。

| 差异类别 | 判断与处理 |
| --- | --- |
| 阻断 | 主操作不可达、内容遮挡/缺失、结构或批准方向严重偏离：修复后才能完成 |
| 重要 | 承诺的层级、换行、间距、素材或响应式行为明显失真：按目标修复，或先明确接受的取舍 |
| 轻微 | 字体抗锯齿等环境差异、合同容差内细节：说明容差依据，不无限逐像素打磨 |

截图回归的黄金基线是审阅后的浏览器渲染，不是自动把设计 JPEG 作为 Playwright expected，也不是把首次生成的截图当作已批准。固定 OS/浏览器与字体环境；差异阈值和动态区域遮罩须有依据，不遮主内容、不自动更新快照制造通过。[Playwright 视觉比较](https://playwright.dev/docs/test-snapshots)

视觉取证留在项目 `.work` 或项目指定产物目录，记录目标版本/commit、入口、视口、状态、参考路径、当前图、差异处置与未验项。使用合成或脱敏数据；不保存密钥、会话凭据或真实用户敏感内容。可复用黄金图经审阅后随目标测试维护在项目仓库，不能只留临时截图。

### 4.2 质量维度不是五套流水线

| 维度 | 触发与最小证据 | 不能替代的事实 |
| --- | --- | --- |
| 视觉 | 可见变更：实际渲染与明确目标对照 | build、DOM 文本匹配不证明外观 |
| 行为 | 受影响主操作、失败、重复提交与恢复：目标 spec/E2E/API | mock 数据不能证明真实集成 |
| 响应式 | 改布局/长文本/共享容器：代表宽度及断点附近，检查局部滚动、裁切、操作可达 | 一张桌面截图不证明所有宽度 |
| 可访问性 | 改控件/弹窗/颜色/动效：键盘路径、焦点进入/返回、可访问名称、非颜色提示、减弱动效；按需自动扫描 | 自动扫描不能证明完整合规 |
| 性能 | 改首屏资源、字体、长列表、依赖或动效：对照输入、资源成本和交互耗时 | 一次 Lighthouse 不能证明真实用户体验 |

可访问性自动扫描的覆盖有限，关键交互仍需键盘等检查。[Playwright 可访问性测试](https://playwright.dev/docs/accessibility-testing)

项目可采用 Core Web Vitals 的良好体验目标：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1，以设备分组的真实用户第 75 百分位衡量；缺少真实样本时明确仅有实验室证据，不能伪称现场指标达标。局部 UI 修正不因此启动全站性能专项。[Web Vitals](https://web.dev/articles/vitals)

## 5. 接入现有交付体系

原 owner 将适用证据加入原任务/机器计划，不新建“UI 计划系统”，也不复制 V0～V5。浏览器工具按当前环境选择；Figma、图像生成和浏览器插件是条件工具，不改变用户所选产品、权限或部署路线。未安装/不可用时采用可用的本地预览与明确基线，必要验收无法执行则报告未闭合。

同一负责人可以依次作设计、实现和核验；阶段边界不是固定职业接力。确需独立视觉评审或互斥页面实现时按既有协作规则；共享 token、AppShell、截图基线、浏览器与状态 owner 不并行争写。

完成需要：目标体验成立、适用行为和视觉证据齐全、重要差异已修复或明确接受、未验项披露。若原任务包含生产问题，必须验证原角色/原入口；本地截图通过不能关闭生产验收。工具受阻或方法无新事实时切换可证伪方案，不降低标准，也不无限重跑。

稳定项目设计归项目，临时差异清单归 `.work`，跨项目方法归 Team OS；不为每次 UI 任务创建 brief、moodboard、spec、report 等固定整套文件。只设计的任务交付设计及实现风险即可，不假称已通过浏览器或生产验收。

## 6. 对研究建议的取舍

| 研究建议 | 采用方式 |
| --- | --- |
| Design first | 先明确体验与可实现约束；新方向先审阅，已定设计直接实施，局部快修不重新画稿 |
| 截图对比 | 作为独立视觉证据；不等于无差别像素相等，也不等于功能正确 |
| 设计系统 | 复用目标项目栈，不把 React/Vite、shadcn、固定圆角/字体数或“禁紫色”变成通用铁律 |
| QA 可观察状态 | 优先原生浏览器与现有夹具，不强制引入全局调试接口 |
| 五维质量 | 合并进原任务的适用验收，不增加五个必跑 Gate 或全量回归 |
| 多角色、Preview | 按风险采用，不强制多模型、独立任务、PR 平台或新部署环境 |
| 示例工时/评分 | 只作研究估算，不作为效率事实或质量评分标准 |
| 固定三张样板与六份设计文档 | 按布局/交互风险选代表屏；现有权威中补缺口，不按目录模板创建文件 |
| 母 Prompt 与十条铁律 | 分解为任务适用的决策规则，不在 AGENTS、Skill 与计划反复粘贴全文 |
| UI 自评 85 分才结束 | 用第 4 节可观察差异与功能证据验收；不以自评分掩盖缺陷或制造无限迭代 |
| 固定库、尺寸和禁用风格 | 作为特定场景示例；产品意图、支持设备和既有系统决定选型与参数 |
