# 通用角色目录

组织角色是可按需加载的职责增量，不等于固定人物、固定模型或常驻进程。同一个 Codex 会话可以在不同任务中承担不同角色，也可以在一个结果内临时叠加专业能力；一个结果始终只有一个负责人。

机器可读的能力与权限目录见 [`capabilities.yaml`](capabilities.yaml)。它用于回答“本次结果需要哪类责任与证据”，不把岗位绑定到固定人物或某一家模型，也不授予某次任务权限。Codex 按需读取目录；任何未来 UI 可用稳定 `role.id` 做展示映射，但不得改变合同语义。

首批通用角色族：

| 角色族 | 核心职责 | 典型产物 |
| --- | --- | --- |
| 总协调/参谋长 | 定界、DAG、负责人、WIP、跨项目路由 | 结果卡、依赖图、决策请求 |
| 产品与架构 | 需求语义、边界、少量方案和长期合同 | 设计决策、验收标准 |
| 端到端交付/Feature Owner | 围绕一个用户结果完成纵向切片、适用验证、集成和文档收敛 | 可运行结果、代码、配置、验证证据 |
| 质量验证 | 可证伪测试、回归边界、证据完整性 | 验证报告、失败复现 |
| 发布与运行 | 构建、发布、回退、运行入口事实 | 发布记录、运行确认 |
| 独立评审 | 正确性、安全、复杂度和权威一致性 | 按优先级排列的发现 |

后续新增角色文件至少说明：使命、拥有的决策、非目标、必读输入、允许写集合、禁止修改、输出合同、验收、时间预算和停止/升级条件。不要为只有名称差异的角色复制完整 Prompt；公共规则引用短内核，角色文件只保留增量。

## 角色、能力、人物与实例

| 对象 | 稳定内容 | 不能替代 |
| --- | --- | --- |
| 组织角色 | 责任、权限、写入和完成合同 | 技术栈能力 |
| 能力画像 | 前端、后端、UX、视觉、数据、安全、测试、SRE 等专业证据和工具 | 结果负责人 |
| 展示人物 | 可选的姓名、外观、沟通风格和默认能力权重 | 自动授权或强制路由 |
| Agent 实例 | 当前 Codex 任务/会话、工作目录和运行状态 | 长期组织制度 |

## 运行时绑定合同

Codex 当前以结果合同中的 `ownerRole` 和 `capabilityProfileIds` 按需绑定角色，不要求先创建人物。未来可视化运行时如保存人物卡，应使用 `roleBinding.id`、角色合同版本和默认能力画像 ID，并遵守三条规则：

1. UI 从本目录展示组织岗位和能力画像，人物模板只提供默认选择和展示备注。
2. 路由按稳定 ID 与本次证据缺口匹配，不按中文描述或显示名做字符串匹配，也不只因角色名称不同而增员。
3. 运行时可缓存上次有效合同，但项目授权、写集合和当前任务边界必须每次重新建立。

`persona`（姓名、形象、沟通风格、人物备注）与 `organizationalRole` 必须分开。角色的 `authority` 和 `writePolicy` 只描述组织分工，始终服从项目合同、本次授权和明确写集合。

软件任务默认由一个端到端 Feature Owner 持有用户结果，再叠加 `capabilities.yaml` 中适用能力。Codex 可以把“前端工程”“UI 设计”“后端工程”作为能力切换或独立协作任务，但不强制每次启动，也不把一个功能切成固定接力流水线。

UI/UX 与前端工程必须保持语义分离：前者拥有用户流程、信息架构、交互状态和视觉验收；后者拥有组件、客户端状态、API 集成、可访问性、性能和浏览器事实。小任务可以由同一 Agent 顺序承担两种能力；新交互体系、复杂状态或高视觉风险才需要独立设计专家。

只有能力/工具确实不同，并且同时出现可独立验收、写集合可分、风险保护或长期高频需求之一时，才实例化专职 Agent。普通 CRUD、局部样式和单服务修改不因文件类型自动拆为前端、后端、测试三个人。
