# TOS0.5 科学协作操作模型

## 1. 核心结论

个人 Agent 团队的默认形态不是“所有角色一起讨论”，而是一个结果负责人根据任务结构，按需调用少量互补专家：

> 默认单 Agent；只有互补证据、真实可分解工作或高风险独立验证能够覆盖协调成本时才组队。团队先独立探索，再在事件节点同步；专业权威随事实移动，写入责任始终单一。

这套合同借鉴人类团队科学，但不把心理学概念直接拟人化到模型。Agent 不会产生人类意义上的心理安全；对应的工程机制是允许报告不确定性、要求提出反例、禁止因角色等级压制证据。

## 2. 四种认知资产

| 团队科学概念 | Team OS 资产 | 最小内容 | 明确不做 |
| --- | --- | --- | --- |
| 共享心智模型 | 结果卡 | 目标、非目标、权威、负责人、风险、验收、当前判别事实 | 广播全部项目文档和 Transcript |
| 交互记忆系统 | 能力目录与项目适配器 | 谁掌握什么、去哪里取权威、能使用哪些工具与权限 | 让每个 Agent 记住所有事实 |
| 情境意识 | 事件化状态与证据引用 | 事实变化、阻塞、风险升级、验收结果 | 高频心跳和自然语言状态刷屏 |
| 组织学习 | 长期使用观察与短复盘 | 保留什么、删除什么、下次只改变哪个变量 | 把一次成功直接提升为永久规则 |

共享心智模型和交互记忆与团队绩效的关联分别得到团队认知研究与元分析支持；关键不是共享更多文本，而是共享任务结构并知道知识位置：

- Shared mental model 研究：<https://pubmed.ncbi.nlm.nih.gov/10783543/>
- Transactive memory systems 元分析：<https://pubmed.ncbi.nlm.nih.gov/30024196/>

## 3. 独立探索与同步节奏

需要多个判断时，参与者先只读取分配给自己的权威与同一结果卡，不看其他人的候选结论。负责人在首轮结束后比较：新增独有证据、互相冲突的假设、共同盲点和可证伪路径，再决定一次综合或追加一轮定向验证。

采用该顺序是为了降低共同信息偏差和过早收敛。团队决策研究显示群体更常讨论共同信息而非独有信息；间歇协作实验则发现，持续互相影响会损害最佳方案质量：

- Hidden profile 元分析：<https://doi.org/10.1177/1088868311417243>
- 间歇协作实验：<https://doi.org/10.1073/pnas.1802407115>

禁止无终点的 Agent 辩论。第二轮必须绑定一个尚未解决的事实差异、反例或验收项；没有新增事实时停止协作并由负责人决策。

## 4. 闭环沟通

只有派工、授权、风险、阻塞、事实变化和完成证明需要跨 Agent 消息。重要派工采用四段闭环：

1. 发送者声明目标、边界、输出位置和完成条件；
2. 接收者回传自己的理解以及不一致点；
3. 发送者只在理解偏差时校准；
4. 接收者以结果和证据引用关闭回路。

这对应 TeamSTEPPS 的 check-back，而不是要求每条消息都回执：<https://www.ahrq.gov/teamstepps-program/curriculum/communication/tools/checkback.html>。

## 5. 高可靠与最小流程

| 风险层级 | 默认阵容 | 保护 |
| --- | --- | --- |
| `low` | 单一负责人 | 直接验收；无强制复盘 |
| `medium` | 负责人，按需一名专家 | 最小 Gate；事实变化才 huddle |
| `high` | 单写负责人 + 独立验证者，按需运行负责人 | 冻结候选、失败关闭、回退和真实入口事实 |

高可靠组织强调对失败保持敏感、拒绝草率简化、关注真实运行、服从专业事实和保持韧性；这里将其收敛为风险分级、专家挑战权、单写者、可恢复和真实证据，不复制高风险行业的完整管理流程：<https://effectivehealthcare.ahrq.gov/products/hro/protocol>。

WIP 默认限制为每个负责人同时一个 `doing` 结果，个人 Team OS 同时最多两个主要结果，其中高风险写任务最多一个。DORA 对 WIP 和小批次的研究入口：<https://dora.dev/capabilities/wip-limits/>、<https://dora.dev/capabilities/working-in-small-batches/>。

## 6. 复盘与规则晋升

高风险任务、明显返工、意外失败或首次使用新拓扑后，执行不超过五问的短复盘：

1. 预期结果是什么？
2. 哪个事实最早区分了正确与错误方向？
3. 哪项协作产生了最终采用的独有证据？
4. 哪个步骤只是重复、等待或上下文搬运？
5. 下一次只改变哪一项规则？

复盘元分析显示结构化 debrief 对绩效具有显著平均收益，但具体效果依赖任务与对齐程度：<https://doi.org/10.1177/0018720812448394>。Team OS 根据真实长期使用中的重复摩擦、有效改进和用户判断晋升规则，不把厂商基准或一次成功直接当作默认策略。

## 7. 软件交付组织模型

软件工作默认围绕一个可被用户验证的纵向价值切片组织，而不是按 UI、前端、后端、测试和运维形成固定接力队列。端到端 Feature Owner 持有结果、集成和完成责任；专业能力在出现真实缺口时临时加入，完成证据后退出。

这套结论组合了三类不同强度的依据：

- DORA 的经验研究支持跨职能、松耦合团队、小批次和减少交接；Team OS 将其转译为端到端 owner、有限 WIP、独立可验收切片和显式接口合同：<https://dora.dev/capabilities/loosely-coupled-teams/>、<https://dora.dev/capabilities/working-in-small-batches/>。
- 社会技术一致性研究表明，协作关系应跟随真实代码/任务依赖，而不是组织名称；结果卡因此记录技术依赖和能力缺口，不能仅凭目录名组队：<https://herbsleb.org/web-pubs/pdfs/Cataldo-Coordination-2013.pdf>。
- Team Topologies 是有价值的行业设计启发而非本地效果证明：Feature Owner 对应面向价值流的端到端责任，能力专家对应短期 enabling，Team OS/Skills/Gate 对应内部平台；复杂子系统只有能独立所有、测试或运行时才形成长期专家边界：<https://teamtopologies.com/key-concepts-content/team-interaction-modeling-with-team-topologies>。

永久按前端/后端分组会增加交接，并可能让组织边界反过来固化系统边界。只有实际模块或服务具有稳定业务所有权、明确接口、独立测试/部署能力和持续工作量时，才把专业能力提升为长期所有者；否则保持一个纵向 owner，由专家给出合同、证据或高风险验证。

开发效率不以代码量、Agent 数量或并行度单独衡量。除结果正确性外，还测量首次判别事实、交接与等待、逃逸缺陷、返工、独立证据、回退准备、Token 和用户纠偏；这与 SPACE 对多维生产力的结论一致：<https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/>。

## 8. 适用边界

近期 LLM 多 Agent 研究提示：工具密集和顺序推理任务可能因协调开销退化，独立拓扑还可能放大错误；同质 Agent 数量增加很快收益饱和。相关结果仍属快速演进研究，应作为长期真实使用中的观察假设，而非产品承诺：

- Agent 系统拓扑与扩展：<https://arxiv.org/abs/2512.08296>
- 同质与异质 Agent 扩展：<https://arxiv.org/abs/2602.03794>

因此，角色名称不构成多样性。有效多样性必须来自不同事实源、工具、模型家族、约束或验证方法，并以最终采用的独有证据衡量。
