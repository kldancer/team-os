# 结论记录：四模型组合（K3 / GLM-5.3 / GLM-5.3-Flash / DeepSeek）的角色矩阵与额度优化

> 性质：设计结论记录，不是执行权威。角色与派工规则权威见 [`../../workflows/context-economy.md`](../../workflows/context-economy.md)；模型组合来源见 [`01-结论记录-无GPT条件下全国产模型替代TeamOS角色判断.md`](01-结论记录-无GPT条件下全国产模型替代TeamOS角色判断.md)；套餐事实与价格见 [`02-结论记录-国产模型Coding套餐组合采购方案.md`](02-结论记录-国产模型Coding套餐组合采购方案.md)。本文件设计 **2026-09-16** 时点的四模型组合工法，实施前需先完成两家登录（见第 8 节）。

## 1. 结论摘要

1. **四模型够用，但要靠"分层派工 + 额度经济学"而不是靠加模型**。真正决定效果的是：谁读原始素材、谁做判断、谁写文件，以及每种模型的额度窗口怎么排。
2. **辅助模型里只有 `k3-256k` 是必用项**（官方明确：`k3` 消耗约为 `k3-256k` 的两倍，质量相同）；`kimi-for-coding` 与 `kimi-for-coding-highspeed` 有明确用武之地（短输出执行/高速迭代）；`glm-5.3-highspeed` 目录可见但官方未文档化（⚠ 计费口径未知）；**`GLM-5V-Turbo` 不值得日常使用**（套餐外、比 Flash 贵约 8 倍，仅作视觉升级路径）。
3. **三个主模型都能身兼多职**，但兼職有硬边界：GLM-5.3 无视觉、K3 不进批量执行、GLM-5.3-Flash 不做跨仓架构判断、DeepSeek 不做最终综合。
4. **执行档的正确选择是 DeepSeek 按量而不是套餐**：本机统计库实测（deepseek-flash 子代理全部历史）新增输入 3.54M、输出 1.90M、缓存读取 385.1M，累计成本仅 **$3.22**——缓存命中率约 99%，按量单价被摊薄到可忽略；把执行塞进 GLM 套餐反而会挤占评审与视觉额度。

## 3. 角色矩阵：主职 / 兼任 / 禁职

| 模型 | 主职 | 可兼任 | 禁职（硬边界） |
| --- | --- | --- | --- |
| **K3**（`k3-256k` 默认 / `k3` 例外） | outcome owner、规划、跨边界设计与状态冻结、最终综合 | ①长文与整仓研究（1M）②诊断假设生成与因果归因 ③对 GLM 评审结论的最终裁决 ④派工包编写 | ①批量机械执行（挤占共享池）②对自家结论做"独立"评审（相关性高，无独立价值） |
| **GLM-5.3** | 深度只读评审（异厂）、failure-surface 复核、跨边界设计挑战 | ①对 K3 的实施规划做红队 ②1M 整仓只读分析（text-only）③复杂诊断的第二假设 ④评审视觉结论的"工程正确性"部分 | ①UI/视觉判断（无图像输入）②日常执行（系数最贵）③最终综合（Owner 职责） |
| **GLM-5.3-Flash** | UI/视觉判断、前端实现循环（看图改代码）、视觉与交互验收 | ①多模态证据采集（截图/图表/文档/视频）②低成本批量执行（系数 ≈ 5.3 的 1/3）③套餐内溢出执行 | ①跨仓架构与合同判断（深度不足）②最终综合 ③高风险独立评审 |
| **DeepSeek V4.1 Flash** | 执行档：侦察、压缩证据包、有界实现、门禁/叶子执行、机械文档 | ①**廉价读图初筛**（图片→事实/文本）②独立模型族反证（对 K3/GLM 结论唱反调）③批量分类与结构化抽取④诊断中的定点观测 | ①最终综合 ②跨边界设计 Owner ③生产写 Owner（须显式授权） |

**组合关系（谁评谁）**：

- K3 出方案 → **GLM-5.3 红队** → K3 裁决（不引入第三种"评审模型"，避免意见发散）
- K3/GLM 出结论 → **DeepSeek 做异厂反证**（便宜且独立族，允许它"找反例"而不出结论）
- 视觉：**DeepSeek 初筛事实 → GLM-5.3-Flash 做判断与修正**（两级，避免用贵模型做读图劳动）

## 4. 辅助模型取舍

| 模型 | 结论 | 用武之地 | 依据 / 风险 |
| --- | --- | --- | --- |
| `k3-256k` | ✅ **必用，日常默认** | Owner 的绝大多数任务（≤256K） | 官方："`k3`（1M）消耗约为 `k3-256k` 两倍"；同等效果 |
| `kimi-for-coding`（K2.8 Preview） | ✅ 值得用 | 有界切片执行、证据整理、结构化输出（输出 ≤32K 足够） | 全档可用、1M 上下文；输出上限 32K 是硬约束 |
| `kimi-for-coding-highspeed` | ✅ 值得用（备选执行档） | 高频小改动、快速迭代、Kimi Code 突发流量 | 需 Allegretto+；受 Kimi Code 5h/周限额（数值未公布） |
| `glm-5.3-highspeed` | ⚠ 先验证再采纳 | 若计费走套餐额度：可做"长输出型评审/实现"（131K 输出） | 智谱官方无文档（404），OMP 静态表挂在 coding 端点；**是否抵扣套餐、积分系数 unknown** |
| `glm-5.2-highspeed` / `[1m]` | ❌ 不必用 | — | 官方口径：调 5.2 自动切 5.3 |
| `GLM-5V-Turbo` | ❌ 不日常用 | 仅当 GLM-5.3-Flash 视觉判断连续失败时的升级路径 | 套餐外按量（z.ai $1.2/$4 每百万），比 Flash 贵约 8 倍；视觉提升幅度未验证 |
| `glm-4.6v`（套餐内 128K 视觉） | ⚠ 备选视觉通道 | 5.3-Flash 视觉能力受限时的对照 | 套餐内但官方未列，口径同 highspeed |

**判断原则**：先用套餐内已付费额度，再用按量；但**执行类负载不要塞进套餐**（见第 6 节经济学）。

## 5. 路由规则（任务类型 × 阶段 → 模型 + 思考强度）

| 任务类型 | 规划 | 实现/取证 | 评审 | 综合 |
| --- | --- | --- | --- | --- |
| 快修（quick-fix） | 会话内直定 | **DeepSeek**（effort high） | 仅跨文件/有风险时 **GLM-5.3**（high） | 会话内 |
| 功能（feature） | **K3-256k**（high） | **DeepSeek**（high）→ 视觉相关交 **GLM-5.3-Flash**（max） | **GLM-5.3**（high） | **K3-256k** |
| 专项（program） | **K3-256k**；跨仓合同冻结点用 **k3** | 切片 **DeepSeek**（high，可并发）；UI 切片 **GLM-5.3-Flash**（max） | **GLM-5.3**（max）+ 逃逸面复核；异厂反证 **DeepSeek** | **k3** |
| UI / 前端 | **GLM-5.3-Flash**（max）出设计判断 | 截图事实先 **DeepSeek** 初筛 → 实现 **GLM-5.3-Flash** 或 **DeepSeek** | 视觉验收 **GLM-5.3-Flash**（max）；工程正确性 **GLM-5.3** | **K3-256k** |
| 诊断（diagnose） | 假设生成 **K3-256k**（high） | 定点观测 **DeepSeek**（high） | 反证 **GLM-5.3**（high） | **K3-256k** |
| 研究 / 长文 | — | 取证 **DeepSeek** | 结论挑战 **GLM-5.3** | **k3**（>256K）或 **K3-256k** |
| 提交 / 机械校准 | — | **DeepSeek** 或会话默认 | 不评审 | — |

**思考强度默认值**（省额度关键）：K3 `high`（长程/裁决用，常规不用 max）；GLM-5.3 `high`（failure-surface 复核才用 max）；GLM-5.3-Flash `max`（视觉判断需要）；DeepSeek `reasoning_effort` 高位（便宜，不必省）。

## 6. 额度经济学与排程

**三条通道的成本结构完全不同**：

| 通道 | 计费 | 实测/官方口径 | 排程建议 |
| --- | --- | --- | --- |
| Kimi 会员（¥199 Allegretto） | 共享额度池 + Kimi Code 5h/周限额 | 官方只给"约 150 个 Agent 任务"；`k3` 消耗是 `k3-256k` 两倍 | **默认 `k3-256k`**；`k3` 只用于 >256K 的整仓/长文档；把 Owner 任务与 Kimi Code 执行分开观察 |
| GLM Coding Plan（¥149 Pro） | 积分：5h 12,000 / 周 60,000 | GLM-5.3 周 2.90–5.80 亿 tokens；Flash 周 8.77–17.55 亿（95% 缓存） | 重评审排**非高峰**（工作日 14:00–18:00 之外 + 周末全天，50% 抵扣）；**不要**把执行负载塞进来 |
| DeepSeek 按量 | token 计费，谷时半价 | 本机实测（全部历史）：新增输入 3.54M + 输出 1.90M + 缓存读取 385.1M = **$3.22**，缓存命中率约 99% | 批量执行/侦察/机械任务**优先放这里**；工作日 9:00–12:00、14:00–18:00 为高峰（¥2/百万输入），其余谷时（¥1/百万） |

**反直觉结论**：执行档用 DeepSeek 按量比用 GLM 套餐额度更划算——因为 agent 负载缓存命中率极高，按量单价被摊薄到可忽略；而 GLM 套餐额度一旦被执行吃掉，评审与视觉就会在 5 小时窗口内被卡死。

**溢出策略（按顺序）**：

1. GLM 窗口打满 → 评审切 `zai` 按量（OMP 内置 `zai` provider，GLM-5.3 ¥8/¥28 每百万）；
2. Kimi 池紧张 → Owner 任务降级 `k3-256k`（若已在用则切 `kimi-for-coding` 做短输出交付）；
3. 全部紧张 → 只做"必须由该模型做"的工作，其余延后到下一个窗口，不静默换模型。

## 7. 上下文策略（与派工包配合）

| 场景 | 策略 |
| --- | --- |
| 日常 Owner 任务 | `k3-256k` + 派工包/证据包（压缩后通常 <100K） |
| 跨仓合同、整仓重构、长文档 | `k3`（1M）——**例外而非默认**，需在任务里显式说明为何要 1M |
| 深评 | GLM-5.3 直接读 diff + 收据摘要 + 定点片段；不整仓灌入 |
| 视觉 | DeepSeek 先把截图/视频抽成"事实清单 + 行号/坐标"，GLM-5.3-Flash 只在该清单上做判断 |
| 派工包 | 保持现有纪律：绝对路径、写集合、禁止读取、内联合同、验收命令；**禁止**用"整仓读取"代替派工包 |

## 9. 风险与待验证

1. **Kimi Code 5h/周限额未公布** → 前 5 个任务记录触发情况；若频繁触发，把执行进一步压到 DeepSeek。
2. **`glm-5.3-highspeed` / `glm-5v-turbo` / `glm-4.6v` 是否抵扣套餐额度未知** → 在智谱用量页核对后再决定是否纳入。
3. **智谱白名单灰区**：OMP 不在官方指定工具列表；若被判定违规可能限流/冻结（详见 doc 02 §2.3）。
4. **Kimi 会员额度是共享池**（网页/研究/Office/Kimi Code 共用），Kimi Code 用超会影响 Owner 可用量。
5. **fallback 不得静默跨档**：套餐额度耗尽后回退按量必须在会话中显式声明，否则违反"fallback 必须披露"与"不得静默改变负责人"。
6. **K3 1M 上下文的解锁档位口径冲突**（Kimi Code 文档称 Allegretto+，帮助中心把"百万 tokens 超长对话容量"列 Allegro）→ 以实测为准。

## 10. 明确不做

- 不把 GLM-5V-Turbo、GLM-4.6V 作为日常视觉通道（套餐外/未文档化）。
- 不用 GLM-5.3 做执行主力（系数最贵且无视觉）。
- 不让 Kimi Code 承担批量执行（共享池 + 未知限额）。
- 不为"多模型"而给同一职责配两家模型；异厂只在**评审/反证**位置保留。
- 不新增第五个模型通道去解决额度问题（先优化排程与分工）。

## 18. 让分档真正自动运行：门禁、派工生成器与归属口径（2026-09-17 13:00）

§17 的根因（执行类工作在订阅档主会话自做、UI 不过视觉档、规划不对半、生产探测直接 ssh）不能只写在文档里，因此本轮把它做成三个可执行机制。

### 18.1 `check_role_routing.py --gate`：收尾强制门禁

- **blocking（阻断 close）**：订阅档主会话直连生产的命令（ssh/scp/docker run|exec|push/kubectl/helm/rsync + 生产地址）；主会话 UI 调用超阈值且零视觉档派工。
- **advisory（只报告）**：owner 自执行占比 >0.30、上下文中位 ≥200k、规划对半 <0.5、1M 晋升次数。
- **任务级归属**：`--task <id>` 先取“最早提到该 id 的会话”作为 owner（对应 `one-outcome-has-one-owner`），只统计该会话及其 lane 子会话，并收敛到首次/末次提及之间的调用；后来只是讨论该 id 的会话不会被算进来（实测：评审会话不再污染 mindie 任务的 UI 计数）。
- **lane 计入**：`parentSession` 指向顶层会话的子会话（lane/证据会话）单独统计为执行档工作量，不再从指标里消失；`executionDelegatedShare` 反映“执行是否真的分流了”。
- **中位口径**：上下文样本只取顶层会话，避免 lane 的小窗口把中位稀释成假达标。
- **UI 标记收紧**：去掉 `console`/`portal` 这类会误伤后端命令的泛词，只保留文件形态与具体界面标识。

实测口径（同一批会话）：
- 全窗口：blocking = 生产命令 91 + UI 无视觉档 2701；advisory = 规划 0.333、owner 自执行 0.597、中位 420k、1M 晋升 1。
- mindie 任务（归属到 owner 会话后）：blocking = 生产命令 **29**；advisory = owner 自执行 **1.0**、中位 **545k**。即该任务的 owner 调用几乎全是执行类，执行分流的 97.6% 是靠 lane 完成的。

### 18.2 `route_work.py`：分档派工生成器

`--type implement|research|ui|plan|review|ops` + 改动路径 → 自动判定档位矩阵并生成自足派工包：

| 输入 | 自动派给 |
| --- | --- |
| implement | 执行档；含 UI 路径时**自动追加视觉档** |
| research | scout 证据包 |
| ui | 视觉档基线 + 执行档实现 |
| plan | 研判档起草 + 分析档裁决 |
| review | 研判档 findings |
| ops | 执行档；含远端路径时追加 prod-env preflight |

`juspctl plan` 的输出现在带 `dispatchHint`（就是这条命令，已按 changed paths 填好）与 `closeGate`，规划完成的当下就把该派给谁摆到面前。

### 18.3 接入日常命令

`juspctl close` 先跑 `--task <id> --gate`：blocking 直接抛 `ControllerError` 阻断关闭（`task_state` 不写入），只能整改或显式 `--skip-role-routing` 覆盖；`juspctl role-routing --task <id>` 可单独查看。team-os 缺席时降级为 stderr 警告，不破坏既有流程。

### 18.4 实测发现的运行时漂移

接入门禁后立刻抓到一处真实漂移：运行时 `config.yml` 的 `default` 被写成 `teamorouter/deepseek-flash:high`（执行档），而目录声明的临时绑定是 `zhipu-coding-plan/glm-5.3:high`（分析档代持）。已按声明恢复；`check_model_routes.py` 与 `check_role_routing.py` 现在能同时抓住“绑定漂移”和“行为漂移”。

### 18.5 残留缺口（诚实记录）

- harness 的 `config.yml` 没有 hook 机制，**无法在调用发生前拦截**订阅档主会话的 ssh/docker；当前是“规则 + 收尾门禁”的事后强制。若要做到事前拦截，需要 harness 侧支持。

**本轮抓到的漂移**：① `default` 曾被写成 `teamorouter/deepseek-flash:high`（执行档），已恢复为目录声明的代持值；
② Kimi 窗口 13:47:25 重置、`usage_history` 报 `ok` 后，`plan_owner` 与 `default` 仍停在 GLM 代持——按 `revertWhen` 应回滚。

**新增两个自动守卫**（`check_model_routes.py`，46 项单测通过）：

1. **可用性校验**：每个角色绑定与 agent 回退链中的 `provider/model` 必须可解析——provider 需出现在 `models.yml` 或内置预设缓存，
   模型 id 需在该 provider 的缓存清单内；两者都缺失时输出 **gap**（`no models.yml or model cache`）而不是把全部 provider 判为未知。
2. **代持过期校验**：`temporaryBindings` 条目仍生效、且 `revertTo` 对应通道的窗口已报 `ok`/`warm`（或已无问题样本）时，
   直接报 issue：`temporary binding for role X is past its revert condition … revert to … and drop the declaration`。

这两个守卫覆盖的正是「配置看起来被打乱」的两类真实原因：**绑定指到不存在的 provider/模型**与**该撤没撤的临时重绑**。

## 19. 复盘整改：把"停线、计划在场、验证在场"做成机制（2026-09-17 晚）

对 `mineru-910a-mindie-office-upgrade` 的复盘（见本轮答复）给出的 5 个缺陷，逐条落成可执行机制，而不是规则文本。

### 19.1 停线：失败预算（team-os）

- 派工包模板 v2（`scripts/route_work.py`）新增四段：**前提与验证状态**（逐条 verified/unknown/risk，`unknown` 不得作为实现方向基础）、**失败预算与停线**（默认 2 轮；同一验收点连续 2 轮 FAIL 或根因不在本包写集合内 → 停手）、**节拍与结构化回报**（每 20 分钟或每步一段；`VERDICT: <验收点> PASS|FAIL` 与 `STOP: <原因>` 为机器输入）、证据引用要求；CLI 暴露 `--failure-budget` / `--cadence-minutes`。
- `check_role_routing.py --gate` 新增：
  - **blocking `failure-budget-exceeded`**：按 `VERDICT <点> FAIL` 计数，或按同一失败文本在 ≥2 条消息中重复（自由文本兜底）判定；`PASS` 只认 `VERDICT … PASS` 这个机器标记（引用目标文本 `ALL CHECKS PASSED` 不算通过——这一条是实测踩出来的）。

### 19.2 计划必须在场（jusuan-installer）

- `juspctl close` 新增**收据门禁**：按 `planId` 关联收据，校验本任务 `requiredLevels`（含 freeze 时的 `freezeLevels`）中每个 `commandId` 都有通过的收据；缺任一条即阻断关闭（`--skip-receipts` 仅限显式覆盖）。这正是"计划声明了 V0/V1/V2 却从未执行"的直接拦截点。
- `juspctl health` 新增两项机器事实：
  - `stalledTasks`：仍处 ready/doing/blocked、超过 2 小时、且**零事件零收据**的任务；

### 19.4 残留缺口（诚实记录）

1. `PASS` 只认 `VERDICT:` 标记，属**新契约**：历史自由文本的成功无法回溯判定，因此旧任务只能报"无成功标记"而不是"确认失败"。
2. 失败签名是文本聚类兜底，叙述里重复引用同一失败串可能重复计数；blocking 语义是"同一失败重复 ≥2 次且无通过标记"，宁可多报不可漏报。
3. 收据门禁要求 Gate 通过 `juspctl apply` 跑过；若团队改用其他执行入口，需要同步写收据，否则会被误判为未执行。
4. `unverifiedDeliveries` 以"计划创建时间 + changed 路径前缀"划分归属；同一路径被后续任务复用时仍可能并入，需人工看提交正文。
