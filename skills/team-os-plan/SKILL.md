# Team OS 结果规划

## 默认输入编译

用户通常只提供自然语言需求，不要求填写结果合同字段。按 [`request-compiler.md`](references/request-compiler.md) 先自动判断意图，读取项目事实并补齐最小合同、Owner、拓扑、验收和停止条件；只有产品决策、高风险授权或事实冲突才向用户提问。需要确定性草案时运行同目录 [`scripts/compile_request.py`](scripts/compile_request.py)，它只分类和生成默认值，不授予权限，也不替代项目机器计划。

## 先建立一个结果

从当前对话提炼并在工作中持续维护：

- `outcome`：用户最终能直接验证的结果；
- `nonGoals`：本次明确不做的事情；
- `authority`：项目 `AGENTS.md`、规范、正式设计和机器入口；
- `scope`：读集合、写集合、明确排除项；
- `acceptance` 与适用验证；
- 目标时间、hard stop 和失败后的可证伪切换条件；
- 一个结果负责人。

不要要求用户重新填写已经在对话里给出的信息。普通 Gate、重试、波次或专家输入是同一结果的事件/子任务，不新建顶层结果。

Goal 只在用户明确要求时创建，并且一个 outcome 只对应一个 durable outcome；它用于长任务持续推进，不证明规划完整，也不因 plan revision、返工或刷新重复创建。Codex 原生 goal、OMP todo/checkpoint 或 Pi 扩展 goal 都只是运行时投影；需要跨 Session 或跨 harness 恢复时，以项目既有机器状态或 `.work` 中的 outcome 和收据为准。

先判定任务意图：已有症状的排查或“定位并修复”是同一个可证伪诊断闭环；新模块仅设计/规划与结论已定后实施不同。只有跨边界、未决依赖或高风险写入才维护含决策基线、场景/失败面、DAG 和验收映射的实施规划；局部快修和单路径刷新用一段最小计划直接执行。需要新建时以 [`references/module-implementation-plan.md`](references/module-implementation-plan.md) 为最小骨架；项目若有更具体模板或要求 program 规划文档，使用项目合同并由其机器入口绑定原文和指纹。不得为了“完整”预先读取或罗列与当前路径无关的文件。

## 再选最小拓扑

默认 `solo`。只有满足下列之一才增加协作任务：

- 不同事实源需要独立首轮，且会产出可比较的独有证据；
- 子结果能独立验收且写集合互斥；
- 高风险候选需要不修改实现的独立验证者。

复杂模块、跨服务结果或两个以上独立证据域在实施前向用户显式给出一次拓扑判断，即使仍是 `solo`。协作须符合当前工具权限，并使用可检查状态、Transcript、模型和停止动作、拥有独立上下文且可单独验收的执行单元：Codex 使用独立任务，OMP 使用 Agent Hub 可见且按写集合隔离的 worker，Pi 只使用已通过 Harness Gate 的 subagent 扩展。当前 Session 的 owner 负责综合；只有用户明确授权且有独有证据收益时才选择其他模型，不因模型名称或角色名称自动升级全员。

分工按四档：**裁决型规划**（跨仓合同、状态冻结、取舍裁决、最终综合）走分析档（`@plan_owner`），**评审型规划草案**（覆盖型规划、接口/失败面矩阵、诊断第二假设）走研判档（`@plan_alt`）且规划类派工至少一半交它，异厂红队与只读深度评审走研判档（`@deep_review`），UI/前端深度设计与视觉判断走视觉档（`@ui_deep`），其余侦察、批量取证、有界实现、门禁/冒烟/刷新/生产事实执行、机械文档与提交准备走执行档（`@fast_worker`）。角色职责稳定，具体模型由 Profile 角色映射按会话或持久配置替换；切换必须显示 resolved model、作用域和恢复方式，不得静默跨 Provider。前三档是订阅额度，只做只有该档能做的事。执行档必须由显式绑定落实（`@fast_worker` 与泛型 worker 的模型覆盖），因为未绑定的子角色继承父 Session 模型；末端机械车道不要求额外角色绑定，也不为它新建角色或会话。

每个派工先写自足派工包（仓库绝对路径、写集合、禁止读取、变更步骤、内联合同、验收命令），下游不从设计正文或规划正文反推意图；分析/研判/视觉档不做原始探索，改由快速只读角色取回带文件/行锚点的压缩证据包。读取与派工的完整规则见 [`references/context-economy.md`](references/context-economy.md)，派工包骨架见 [`references/worker-pack.md`](references/worker-pack.md)，两者随 Skill 一并安装。

需要协作时，为每个真实独立任务声明：目标、非目标、输入、写集合、禁止修改、验证、时间预算、完成条件和停止条件。先画依赖 DAG，再并发；写集合重叠则串行或保持单一写者。当前主任务负责综合和跨 Lane Gate。

大模块按用户可运行的纵向场景切片，不按前端/后端/UI 目录机械分包。每个验收/场景都有 owner 与证据，每个受影响的跨边界失败都有拒绝、恢复或明确非目标；未变部分引用仍适用的证据，不重建全平台矩阵。未决业务问题只阻塞依赖分支，独立部分继续；同一 outcome 的遗漏沿用原 task ID，先本地合并闭合再冻结一个候选。

协作完成按“产物位置、实际变更、验证证据、剩余风险”验收，而非状态话术。文档迁移对照旧→新合同并检查旧规则残留；共享文档删除由负责人在验收后统一处理，不交给互斥 Lane 顺手清理。

只有需要显式选择专业角色或独立任务时，才读取 [`references/capabilities.yaml`](references/capabilities.yaml)。从中选择最少的稳定 `role.id` 和 `capabilityProfile.id`；简单 `solo` 任务不读取目录，也不因角色名称创建额外任务。该文件是安装时从 Team OS 权威目录生成的只读投影，本次任务授权仍由项目合同决定。

## 路由到项目流程

读取当前目录的项目指令。若项目提供 `design`、`deliver-change`、`diagnose`、`review`、`ship-changes` 或机器 planner，只选一个流程所有者并把结果合同交给它；本 Skill 不建立第二套任务数据库、不替代项目 Gate、不扩大授权。项目机器任务支持稳定 task ID 时，重规划沿用同一 task ID，不把 Plan、重试或波次升级为新结果。

自然语言编译完成后，Owner 必须把 `executionContract` 落到项目机器入口：实现/验证/恢复请求调用项目 planner，生产或远端请求在冻结收据和 `remote-preflight` 通过前不得调用底层 refresh/deploy 脚本；“按现有/以上结论”优先恢复已有 taskId，而不是只依赖当前 Transcript。底层执行器只能消费已签名计划和对应 stage，不能成为计划的替代入口。

## 完成

只有 outcome、适用验证、必要运行事实和已知风险披露闭合才完成。动态收据写项目指定 `.work`；长期合同只进入项目或 Team OS 的唯一权威位置。若项目提供机器任务关闭入口，把已知的首次判别事实耗时、返工、用户纠偏和交接次数写回原任务；模型 token、上下文体积与重复读取用项目统计入口汇总，缺失值记 null，不猜零。
